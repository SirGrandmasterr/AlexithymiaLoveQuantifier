## Reading

**Nothing here is a fact about a model.** The `reference` candidate answers every case with
the golden suite's own hand-written proposal, so 100 % on all three feeling criteria is the
only result that would not have been a bug. What it does establish, on 2026-09-03:

- **The harness computes what §5.7 asks for, end to end.** 120 cases were scored, 126 required
  ids checked, 96 forbidden ids checked, 20 ambiguity cases counted, and every answer was run
  through the app's own `validateProposal` — `dropped_by_filter` was 0 and all 120 were
  schema-valid before filtering, which also re-proves offline what
  `src/journal/inference/validate.test.js` proves in `npm test`.
- **The gate refuses to call an unmeasured criterion a pass.** The verdict is `incomplete`, not
  `pass`, because the German-versus-English WER margin could not be measured: the suite has no
  recordings on this machine, so there are no clean clips in either language. That is the
  behaviour §12.1 asks for, and it is the reason the verdict has three values instead of two.
- **The ambiguity criterion has something to bite on.** 20 of the 120 cases expect a value
  other than `none` — 12 `feeling`, 6 `target`, 2 `conflict`. At §5.7's 0.9 the criterion fails
  on the third wrong answer, which is tight enough to matter and loose enough that one case
  does not decide a tier default. A model that answered `none` everywhere would score 0.833 on
  *every case* and **0.0** on this criterion, which is the split the two rows in *The numbers
  the gate reads* exist to make visible.
- **The suite is balanced by language.** 60 English and 59 German by what is spoken, plus the
  one French case that D1 put in on purpose. So the margin comparison, when there are clips to
  make it from, will be a comparison of two languages and not of two different sets of
  sentences: every case has a half in each.

**No threshold moved.** All four are as `gate.mjs` received them: three from §5.7 verbatim, and
the German margin (0.05 absolute, clean clips) stated by this session with its reasoning in
that file. §5.7 says to revise them after the first run against a real model — this was not
that run, and revising a threshold against the reference answers would be revising it against
nothing.

## What this run does not say

- **No weights were loaded and no model answered anything.** Every number above came from the
  hand-written references in `src/journal/inference/golden/transcripts.json`.
- **No recordings exist yet.** The suite calls for 240 clips — 120 cases × clean and noisy —
  and has none. Every audio-mode candidate therefore has nothing to run, and the WER half of
  §5.7 is entirely unmeasured. `make journal-audio-check` lists what is missing;
  `product_vision/eval/recording-script-{en,de,fr}.md` are what a recording session is run
  from, and `src/journal/inference/golden/audio/README.md` says where the files go.
- **The two CLI argument templates have never been run against a real binary.** There is no
  llama.cpp and no LiteRT-LM build on this machine. They come from the two projects'
  documented interfaces, both are overridable in one environment variable, and the report
  prints the command that actually ran — but the first real run should expect to correct them.
- **Peak memory and latency are meaningless here**, because no process was started. When a
  process is started they are a sampled floor and a wall clock including model load, and the
  harness README says which is which.
- **The web tier remains unmeasurable by this harness.** `full-web` stands in for
  transformers.js over WebGPU with llama.cpp over the same upstream weights; a pass there is
  evidence about the model and not about the runtime the browser actually uses. D3's warning
  that the web model has never run is unchanged by this session.
